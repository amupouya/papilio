# Papilio 4.0.0

Use `PermutedBigIntField` to generate a nonsequential BIGINT directly in any
PostgreSQL column. The caller chooses `primary_key=True` or `unique=True`.
The helper works on BaseEntity; overriding `id` on IdentifiedEntity or
PersistenceEntity retains the existing ready PostgreSQL repositories.
See [usage, PostgreSQL setup and migration DDL](../guide/permuted-fields.md).

## Breaking removal of the separate public-ID family

Removed `PGPublicIDField`, `PGPublicIdentifiedEntity`,
`PGPublicPersistenceEntity`, both `PGPublic*Repository` classes and their
contracts, and `PublicIDOutput`. No compatibility aliases are supplied.
IDEncryption remains removed. Payload encryption is unchanged.

Use ordinary model/repository/contract families and `BaseOutput`. Repository
`get_by_id` and foreign keys use the one stored ID. IdentifiedEntity.to_row now
retains a database-assigned ID even when native ORM loading did not add it to
Pydantic's explicit fields; updating/upserting a loaded row keeps its identity.

## Existing data requires an application-owned migration

Changing a Python field declaration does not replace an existing primary key,
rewrite foreign keys, or preserve already issued URLs automatically. Choose an
explicit mapping/cutover for every affected table and its references before
upgrading. No application data migration is executed by this package.

If the existing 3.0 public_id values must become the primary IDs, first materialize
the internal-ID-to-public-ID mapping and rewrite every dependent reference using
it. The old generated expression depends on the old id; remove that dependency
and preserve its stored values before replacing/dropping/renaming columns and
rebuilding PK/FK constraints. Include external references, events and URLs in the
cutover. Do not simply assign a new generator or reset a sequence to max(id).

To continue a preserved mapping without collisions, the new sequence/default
must reproduce the old range_encrypt_element mapping and resume strictly beyond
every old allocation, including rollback/deletion gaps. A fresh permute_nextval
sequence with a different input interval does not reproduce the old mapping.
Keeping the old DB generation design temporarily, retaining old identifiers as
legacy references, or choosing a proven new allocation interval are explicit
application migration choices. There is no safe generic automatic rewrite.

For fresh tables, use the documented NO CYCLE sequence/default and keep its range
and parameter fixed. Bounds, exhaustion, explicit-value insertion, schema naming,
ordering and extension requirements are described in the field guide.
